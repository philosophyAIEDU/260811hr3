# 그로우패스 — 폴더 구조 · 데이터 구조 · 직무별 요구수준 표 (1단계)

이 문서는 요청서의 "작업 순서 지시 1번" — 폴더 구조, 데이터 구조, 직무별 요구수준 표 — 를
확인받기 위한 문서입니다.

> **[변경 이력]** 원래 요청서는 "로컬 SQLite, 사내망 전용, 클라우드 업로드 금지"를 전제로
> 했지만, 이후 "Netlify에서 배포"로 방향이 바뀌었습니다. 이에 따라:
> - 데이터베이스를 로컬 SQLite 파일 대신 클라우드 저장소로 옮겼습니다. 처음엔 Netlify
>   DB(Neon Postgres)였지만, 대시보드에서 DB를 따로 연결해야 하는 단계가 실제로 막힘
>   지점이 되어 **사용자 요청으로 Netlify Blobs로 다시 전환**했습니다 (연결 단계 없이
>   배포만 하면 바로 동작 — 15번 항목 참고).
> - 이 변경은 §7 "개인정보 및 보안 요구사항"의 원래 전제와 다르다는 점을 알려드립니다.
> 아래 표 형식(직원/진단회차/역량점수/추천결과)과 항목 이름은 원 요청서와 동일하게 유지했습니다.
>
> (한때 사이트 전체 접속코드(`/enter`)를 추가했었지만, 사용자 요청으로 제거했습니다.
> 또한 사번·이름 입력도 사용자 요청으로 없앴습니다 — 지금은 브라우저가 자동 발급하는
> 무작위 식별번호로 본인을 구분합니다. 17번 항목을 참고해 주세요.)

## 2. 데이터 구조 (Netlify Blobs에 저장하는 JSON 문서 구조)

요청서 "4. 데이터 구조"의 4개 표를 `lib/db/store.ts`의 TypeScript 타입으로 옮겼습니다.
(원래 SQLite → Postgres 테이블이었으나, 15번 항목에서 설명하는 이유로 지금은 SQL
데이터베이스가 아니라 **Netlify Blobs 안의 JSON 문서 하나**에 배열 형태로 저장합니다.
표 형식과 항목명은 요청서와 동일하게 유지했습니다.)

| 요청서 표 | 실제 이름(JSON 배열) | 비고 |
|---|---|---|
| 직원 | `employees` | `employee_id`가 고유 식별자. 지금은 사번이 아니라 **브라우저가 자동 발급한 무작위 식별번호**가 들어갑니다 (17번 항목) |
| 진단회차 | `assessments` | 한 사람당 여러 번 쌓임 → 이력 비교 기능의 기반 |
| 역량점수 | `scores` | 진단 1회당 10개(역량 10개) |
| 추천결과 | `recommendations` | AI가 만든 추천 + 학습 상태(예정/수강중/완료) |
| (추가) 설정 | `settings` | 요청서에 없던 항목이지만, Gemini API 키(공용)를 저장하기 위해 추가했습니다. 키 자체는 git에 올라가지 않고 Netlify Blobs 안에만 저장됩니다. |

개인이 자기 API 키로 "덮어쓰기"하는 기능은 별도 로그인이 없으므로, **그 직원의 브라우저에만
저장**(로컬 저장소)하고 화면에서 그 값이 있으면 그 값을, 없으면 관리자가 저장한 공용 키를
사용하는 방식으로 만들었습니다. (서버에 개인별로 저장하지 않음 — 사번마다 키를 넣게 하면
관리 부담과 유출 위험이 커지므로 브라우저 저장 방식을 택했습니다.)

전체 타입 정의는 `lib/db/store.ts` 파일에서 보실 수 있습니다.

## 4. 그 밖에 이번 단계에서 정한 것

- **Gemini 모델명**: `lib/config/constants.ts`의 `GEMINI_MODEL` 상수 한 곳에서 관리 (`gemini-3.5-flash-lite`)
- **관리자 코드**: `lib/config/constants.ts`의 `ADMIN_CODE` 상수 (기본값 `1234`)
- **역량 갭 기준**: 요구수준 − 현재점수 ≥ 2 이면 "우선 보완"
- **재진단 안내 기준**: 완료 항목 3개 이상 쌓이면 배너 표시
- **휴넷 링크**: 실제 검색 주소 형식을 아직 확인하지 못했으므로, 우선 휴넷 메인 주소로 연결 +
  검색어 클립보드 복사 버튼 방식으로 계획 (요청서 지침대로 주소를 지어내지 않음)

## 10. AI 프롬프트 및 JSON 응답 형식 설계 (+ 화면4 완료)

`npm run build`가 계속 통과하는 상태로 이어가기 위해, 아래 설계를 바로 적용해 화면4까지
함께 만들었습니다. 마음에 안 드는 부분이 있으면 언제든 말씀해 주세요 — 프롬프트는
`lib/gemini/recommendPrompt.ts` 한 파일만 고치면 됩니다.

**개인정보 처리 원칙**: 프롬프트에는 이름·사번을 절대 넣지 않습니다. Gemini에는
"현재직무 / 희망직무 / 커리어목표 / 역량별 현재점수·요구수준"만 전달합니다.

**프롬프트 요지** (`buildRecommendPrompt`):
1. 요구수준−현재점수 격차가 큰 역량을 우선하되 전체 성장도 고려
2. 추천 6~9개를 "사내강의"(플랫폼=휴넷) / "외부주제"(인프런·유데미·코세라 등) / "도서" 3구분에서 섞어서 생성
3. 각 항목에 "3개월"/"6개월"/"12개월" 단계를 배정 (3개월에 최소 1개 이상 포함 → 성장 로드맵)
4. search_keyword는 실제 검색용 키워드만 (URL·ISBN 등 확인 불가한 정보는 지어내지 않도록 명시)
5. reason은 역량 격차·커리어 목표와 연결한 1~2문장
6. JSON 형식 외 다른 문장·마크다운 금지 (+ Gemini generationConfig에 `responseMimeType: "application/json"` 지정)

**응답 JSON 형식**
```json
{
  "recommendations": [
    {
      "category": "사내강의 | 외부주제 | 도서",
      "title": "짧은 제목",
      "search_keyword": "검색용 키워드",
      "platform": "휴넷 | 인프런 | 유데미 | 코세라 | 도서 등",
      "reason": "추천 이유 1~2문장",
      "stage": "3개월 | 6개월 | 12개월"
    }
  ]
}
```
`parseRecommendResponse()`가 이 형식을 검증하고, category/stage 값이 정해진 목록에 없거나
title·reason이 비어 있으면 그 항목만 걸러냅니다. 통과한 항목이 하나도 없으면 오류로 처리해
화면에 "잠시 후 다시 시도해 주세요" 안내가 나갑니다.

**만든 파일**

| 파일 | 역할 |
|---|---|
| `lib/gemini/recommendPrompt.ts` | 프롬프트 생성 + 응답 JSON 검증 |
| `app/api/recommend/route.ts` | GET(기존 추천 조회, AI 재호출 없음) / POST(Gemini 호출 → 검증 → `recommendations` 테이블에 저장, 같은 진단 회차의 기존 추천은 새 결과로 교체) |
| `app/recommend/page.tsx` | 화면4 — 추천이 없으면 "만들기" 버튼, 있으면 3개월/6개월/12개월로 묶어서 표시 + "다시 만들기" + 검색어 복사 버튼 |

- 개인 키가 설정되어 있으면(화면7) 그 키로, 없으면 공용 키로 호출합니다. 둘 다 없으면
  "설정 화면에서 Gemini API 키를 먼저 등록해 주세요" 안내와 함께 설정 화면 링크를 보여줍니다.
- 추천은 진단 회차(assessment_id)당 한 세트로 저장되어, 다시 방문해도 AI를 다시 부르지 않고
  저장된 결과를 그대로 보여줍니다("다시 만들기"를 눌러야 재생성).
- `npm run build` 정상 통과 확인했습니다. (실제 Gemini 호출 결과는 API 키를 등록한 뒤 확인 가능)

## 15. DB 연결 단계 제거 → Netlify Blobs로 전환 (사용자 요청, MVP 우선)

Netlify DB(Neon Postgres)를 대시보드에서 직접 연결해야 하는 단계가 실제로 막힘 지점이
되었습니다(사번 확인 시 "데이터를 불러오는 중 문제가 발생했습니다" 오류). 사용자 요청으로
**DB 연결 단계 자체를 없애고, Netlify에 기본 내장된 Netlify Blobs로 전환**했습니다.
Netlify Blobs는 대시보드에서 따로 연결/설정하지 않아도 Netlify에 배포하는 순간 바로
동작합니다.

**바뀐 점**
- `lib/db/db.ts`(Postgres 연결) + `lib/db/schema.sql` 삭제 → **`lib/db/store.ts`** 신설
  (직원/진단/역량점수/추천/설정 전체를 JSON 문서 하나로 Netlify Blobs에 저장)
- `app/api/employee`, `diagnosis`, `recommend`, `learning-status`, `settings`,
  `admin`, `admin/export` 라우트를 전부 SQL 대신 `store.ts` 함수 호출로 다시 작성
- `lib/db/seed.ts`도 SQL 대신 `store.ts` 함수를 쓰도록 수정 (실행 방법은 위 14번 항목 참고)
- `package.json`: `@neondatabase/serverless` 제거, `@netlify/blobs` 추가
- `.env.example`, `실행방법.md`에서 "Netlify DB 연결하기" 단계 삭제

**표 형식은 그대로 유지**: 직원/진단회차/역량점수/추천결과라는 원래 데이터 구조(요청서
"4. 데이터 구조")는 그대로 두고, 그릇만 SQL 테이블에서 JSON 문서로 바꾼 것입니다.
`docs/데이터구조.md` 2번 섹션의 표 형식·항목 이름은 여전히 유효합니다 (SQL 문법 설명만
지금은 맞지 않습니다).

**알려드려야 할 한계**: 요청 여러 개가 아주 짧은 시간에 동시에 데이터를 쓰면, 나중에 쓴
내용이 앞의 내용을 덮어쓸 수 있습니다(전체 JSON을 읽고 고쳐서 다시 쓰는 방식이라 트랜잭션이
없음). 사내 소규모 인원의 MVP 테스트 단계에서는 문제될 확률이 낮다고 판단해 이대로
진행했지만, 정식 운영 규모로 커지면 정식 데이터베이스로 다시 옮기는 것을 권장드립니다.

`npm run build`, TypeScript 타입 검사 통과를 확인했고, `next dev`(Netlify 연결 없이)로
실행했을 때 예상대로 "Netlify Blobs 환경이 설정되지 않았다"는 오류가 나는 것도 확인했습니다
— 이는 정상이며, Netlify에 배포하면(또는 `netlify dev`로 실행하면) 자동으로 해결됩니다.
제가 이 환경에서 실제 Netlify 배포/Blobs 저장까지 직접 확인하지는 못했습니다.

## 16. 실제 동작 검증 (이번 단계에서 처음으로 제대로 수행)

지금까지는 `npm run build` 통과만 확인하고 "실제로 돌려보지는 못했다"고 말씀드렸는데,
이번에 **로컬에서도 실행 가능하도록 만든 뒤 전체 흐름을 실제로 호출해서 검증**했습니다.

### 검증할 수 있게 만든 변경

`lib/db/store.ts`가 저장 위치를 스스로 판단하도록 했습니다.

| 실행 위치 | 저장 위치 | 준비 작업 |
|---|---|---|
| Netlify 배포 사이트 | Netlify Blobs | 없음 |
| 내 컴퓨터(`npm run dev`) | `.data/growthpath.json` | 없음 |

판단 기준으로 환경변수(`NETLIFY`)를 짐작하지 않고, **실제로 Blobs를 쓸 수 있는지 직접
시도해서** 구분합니다. 환경변수로 짐작했다면, Netlify 런타임에 그 변수가 없을 경우
서버리스 함수가 곧 사라질 임시 디스크에 저장해서 **데이터가 조용히 날아가는** 사고가
날 수 있었습니다.

### 이번에 발견해서 고친 실제 버그 2개

1. **방금 저장한 데이터가 안 보일 수 있는 문제**
   Netlify Blobs는 기본적으로 "방금 쓴 내용이 잠시 뒤에야 보이는" 방식입니다.
   그대로 뒀다면 진단을 제출하고 결과 화면으로 넘어갔을 때 **방금 낸 결과가 비어 보이는**
   증상이 났을 것입니다. 읽을 때 강한 일관성(strong)을 요청하도록 고쳤습니다.

2. **강한 일관성을 지원하지 않는 환경에서 앱 전체가 죽는 문제**
   1번을 고치면서 새로 생긴 위험입니다. 강한 일관성 읽기를 지원하지 않는 실행 환경에서는
   읽기가 통째로 실패하면서, 사용자가 이미 겪었던 **"데이터를 불러오는 중 문제가
   발생했습니다"** 오류가 똑같이 날 수 있다는 것을 테스트로 확인했습니다.
   지금은 그런 환경이면 일반 읽기로 한 단계 낮춰서 계속 동작하도록 고쳤습니다.
   (가짜 Blobs 서버를 띄워 지원/미지원 두 상황을 모두 만들어 확인했습니다)

또한 모든 API에 `dynamic = "force-dynamic"`을 지정해, Next.js가 응답을 저장해두고
옛 데이터를 보여주는 일이 없게 했습니다.

### 실제로 호출해서 확인한 항목

개발 서버를 띄우고 API를 직접 호출해 확인했습니다. **8개 항목 전부 통과**했습니다.

- 신규 사번(`2023555` / `김필로`) 미등록 판정 → 등록 → 등록 직후 바로 조회됨
- 이름이 다르면 조회 거부
- 진단 제출 → 요구수준이 희망직무 기준으로 자동으로 채워짐
- 진단 직후 결과 조회 시 역량 10개가 바로 보임 (위 1번 버그가 고쳐졌는지 확인)
- 점수가 1~5를 벗어나면 거부
- 관리자 코드 틀리면 거부 / 맞으면 통계 표시, 계산값 수기 검산 일치
- 엑셀 다운로드: 실제 xlsx 파일 생성, 시트 2개·11행·역량 10개 열 모두 확인
- API 키 없이 AI 추천 요청 시 안내 문구 표시

추가로 확인한 것:
- 샘플 데이터 10명 시딩 스크립트 **실제 실행 성공** (이전엔 검증 못 했던 부분)
- 학습상태 변경: 완료 → 완료일 자동 기록, 되돌리면 완료일 삭제
- **다른 사람의 학습 항목은 변경 거부됨** (본인 확인이 실제로 작동)
- 진단 2회 한 직원의 이력이 최신순으로 정확히 조회됨
- 화면 7개 전부 HTTP 200, 런타임 오류 없음

### 아직 확인하지 못한 것 (솔직하게 말씀드립니다)

- **실제 Netlify에 배포한 상태**에서의 동작. 이 작업 환경에서는 사용자님의 Netlify
  계정에 접근할 수 없습니다. Blobs 경로는 가짜 서버로 흉내 내어 검증했고, 실제 배포
  환경과 다를 가능성은 낮다고 보지만 100%는 아닙니다.
- **Gemini API를 실제로 호출한 AI 추천 결과**. 유효한 API 키가 없어서, 키가 없을 때의
  안내 문구까지만 확인했습니다. 키를 등록하신 뒤 추천이 잘 나오는지 봐주세요.

## 17. 사번·아이디 입력 제거 (로그인 없이 바로 시작)

사용자 요청으로 **사번이나 아이디를 전혀 입력하지 않고 바로 쓸 수 있게** 바꿨습니다.

### 어떻게 본인을 구분하는가

첫 방문 때 브라우저가 **추측 불가능한 무작위 식별번호**를 하나 만들어 localStorage에
저장하고(`lib/session.ts`), 그것으로 본인 데이터를 찾습니다. 사용자는 이 과정을 알 필요가
없고, 화면에는 "바로 시작하기" 버튼만 보입니다.

**보안상 오히려 개선입니다.** 기존 "사번+이름" 방식은 사번에 규칙이 있어(E2024001 다음은
E2024002…) 남의 것을 추측해 볼 수 있었지만, 무작위 식별번호는 추측이 불가능합니다.
그래서 이름 대조 절차를 없애고 식별번호 자체를 본인 확인 수단으로 삼았습니다.

### 바뀐 것

| 구분 | 이전 | 지금 |
|---|---|---|
| 화면1 | 사번·이름 입력 후 확인 | **버튼 하나로 바로 시작** |
| 부서·현재직무 | 등록 시 필수 | 진단 화면에서 **선택 입력** |
| 이름 | 필수 | **선택 입력** (화면에서 부를 호칭용) |
| 본인 확인 | 사번 + 이름 대조 | 브라우저 자동 발급 식별번호 |
| API 파라미터 | `employee_id` + `name` | `user_id` |

- `app/api/employee` 라우트는 더 이상 쓰이지 않아 삭제했습니다. 진단을 처음 제출할 때
  `upsertEmployee()`가 자동으로 등록해 줍니다.
- 부서를 입력하지 않은 사람은 관리자 통계에서 **"미입력"** 으로 묶여 집계됩니다.
- 엑셀의 "사번" 열은 실제 내용에 맞게 **"식별번호"** 로 이름을 바꿨습니다.

### 알아두셔야 할 점 (트레이드오프)

로그인이 없으므로 식별은 브라우저에 묶입니다. 따라서 **다른 기기나 다른 브라우저에서
접속하면 지난 결과를 볼 수 없고 새 사람으로 인식**됩니다. 브라우저 데이터를 지워도
마찬가지입니다. "입력 없이 바로 시작"을 우선한 결과이며, 기기 간에 이어서 보게 하려면
로그인이 필요합니다.

### 검증 (실제 호출로 확인, 6/6 통과)

- 첫 방문 시 이력 0건 → **이름·부서·직무를 전부 비운 채로** 진단 제출 성공
- 제출 직후 결과 조회에서 역량 10개 정상 표시
- 선택 입력(이름·부서·직무)을 채운 진단도 정상 저장
- **사용자 A와 B의 데이터가 서로 보이지 않음** (식별번호로 격리)
- 부서 미입력자가 통계에 "미입력"으로 집계됨
- 본인은 학습 상태 변경 가능, **남의 항목은 변경 거부됨**
- 화면 7개 모두 정상 렌더링, 서버 오류 없음, `npm run build` 통과
